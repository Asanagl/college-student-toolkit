# v0.4.0 ACM 对拍功能架构记录

更新日期：`2026-09-01`

> 状态说明：本文记录 v0.4.0 的对拍架构与边界；产品当前版本为 v0.5.0，
> 实现和发布状态以 [`docs/v0.5.0-release-notes.md`](v0.5.0-release-notes.md) 为准。

## 目标与已确认边界

- 新增独立的 ACM 对拍页面，不嵌入单文件 Workbench 页面。
- 页面提供标准程序、待测程序两个独立 C++ 编辑器，以及一份仅存在于当前页面会话的 stdin 输入框；首次打开均为空。
- 两份源码均支持打开文件、保存和另存为。未保存编辑内容不写入历史记录；关闭或刷新页面后丢弃。用户主动保存的文件仍由文件系统保留。
- 每次点击开始都重新编译两份源码，使用当前 ACM 编译器选择和相同 C++17 参数；标准程序编译/运行完成后才进入待测程序阶段，禁止复用旧可执行文件。
- 标准程序源码沿用 2 MiB 输入边界；待测程序源码不设固定的产品输入长度上限，打开、保存、另存为和直接粘贴执行都沿用 `diff-candidate` scope。两个程序各自使用独立临时目录和现有主进程安全兜底：编译 30 秒、运行 3 秒、stdin 256 KiB、stdout/stderr 各 4 MiB、临时目录 128 MiB。待测源码在写入临时目录前后都做配额检查，超出执行期物理配额时返回 `ACM_RUNNER_OUTPUT_LIMIT`；运行时限制不可由页面调整。
- 标准程序非零退出、超时、输出/临时目录超限或编译失败时，结果为“标准程序失败/对拍无效”，不运行待测程序，不产生 AC/WA。
- 待测程序失败使用独立状态（编译失败、运行超时、运行异常、输出/临时目录超限），不产生 AC/WA。
- 两侧正常退出（`exitCode = 0`）后，按所有空白字符切分 token 并逐 token 比较；token 内字符必须完全一致。
- AC 显示“输出一致”并展示两侧受限制的 stdout/stderr；WA 额外返回首个差异，前后各 3 个 token，并标记缺失或多余 token。输出沿用 stdout/stderr 各 4 MiB 上限，不传输退出码或耗时给 Renderer。
- 每个临时可执行文件在程序结束后立即删除；删除失败不阻断结果，返回清理警告并在主进程有限次数后台重试。若终止未确认导致清理被推迟，比较结果仍先发出；迟到的 `exit/close` 清理完成后会补发 `cleanupConfirmed`，并把后续清理警告带回页面。
- ACM 插件禁用/不支持时页面可查看但不能执行；IPC handler 继续执行主进程插件门禁。
- 对拍和 Runner 只面向用户本人信任的本地 C++ 源码；目标程序继承当前用户权限。Job Object/native helper 只负责进程树归属与终止，不提供文件系统、网络或令牌沙箱；不可信源码不应在此版本运行。
- Workbench 和对拍页共享一个持久化的提示关闭状态。关闭后两页均隐藏；插件禁用、应用版本变化或用户主动打开 ACM 设置时重新显示。

## 架构图与数据流

```text
ACM Diff Renderer (/acm-diff)
  ├─ 两个 CodeMirror 编辑器 + stdin（页面内存）
  ├─ 共享 PluginNotice 状态（持久化 dismiss marker）
  └─ window.api.acm.startDiff / onDiffEvent / open/save document
       ↓ preload 最小白名单
Main IPC handlers + zod
  ├─ AcmPluginService 门禁
  └─ AcmDifferService
       ├─ AcmCompilerService（同一编译器/flags）
       ├─ AcmRunnerHelper（Job Object / taskkill fallback）
       ├─ AcmRunnerService 限制/临时目录策略复用
       ├─ token comparator（首个差异 + 3 token context）
       └─ 受限 stdout/stderr 收集（各侧最多 4 MiB）
```

对拍服务保持单一活动任务。一次任务内部依次执行：`reference-compile → reference-run → candidate-compile → candidate-run → compare → cleanup`。每个阶段发出带 `side` 的事件；运行阶段的 stdout/stderr 只在主进程内存中保留至比较完成，IPC 终结事件携带受限制的两侧输出和差异片段。源码 staging 使用可等待的异步写入，在写入前按 UTF-8 字节数预检并在写入后复核目录大小；阶段完成后立即释放任务中的源码引用，避免长时间持有重复副本。主进程还校验 diff 专属 scope 只能由 `#/acm-diff` 路由使用，普通 Workbench 不能自行选择待测源码策略。开始请求只在 ACM 生命周期队列中完成短暂准入检查，随后以可取消的 detached 任务执行；这样编译器探测期间的停止/禁用请求可以立即到达服务，而活动任务守卫仍阻止并发执行。对拍服务开始处置后立即关闭新任务准入，并复用同一个处置 Promise；手动停止、超时、输出超限和流错误都通过有限终止尝试处理。若终止仍未确认，阶段事件/比较结果带 `terminationError` 与 `cleanupBlocked`，活动任务和临时目录继续保留，直到晚到的 `exit/close` 事件确认后再清理；这保证服务不会在失去子进程跟踪后静默允许下一次任务。每个清理重试目标最多登记一个有界重试 Promise，同时全局最多保留 8 个 pending retry；超出上限时只记录 warning 并保留 owner marker，转交下次启动清理。`dispose()` 在停止活动任务后等待已登记重试完成；若子进程仍未确认退出，会明确记录外部进程可能残留，但不会无限等待。重试会重新检查根目录和目录内部的 reparse point，且只针对当前任务生成的路径。文件服务对打开/外部检查使用最多 64 个在途操作的可等待 gate，并按文档、路径和完整指纹复用相同的 in-flight 检查；保存使用最多 4 个在途请求的有界队列并拒绝同一文档重复保存，另存为原生对话框最多同时排队 4 个。退出时先拒绝新操作，再等待已准入的打开、保存、另存为对话框和对拍清理重试完成。

## 模块职责与接口契约

| 模块                               | 职责                                                                                |
| ---------------------------------- | ----------------------------------------------------------------------------------- |
| `AcmDifferService`                 | 校验两份源码和 stdin，编排双编译/双运行，应用标准程序门禁，汇总结果，安排清理重试。 |
| `AcmTokenComparator`               | UTF-8 文本按 `\\s+` token 化，返回 AC 或首个差异及双方前后 3 token。                |
| `src/shared/types.ts`              | 对拍请求、事件、结果、提示 marker 和 IPC API 的唯一契约。                           |
| `src/main/validation.ts`           | 对拍请求、保存/打开参数和提示 marker 的 zod 边界校验。                              |
| `src/main/main.ts` / `preload.ts`  | 注册并暴露最小白名单；handler 先检查 `AcmPluginService.isEnabled()`。               |
| `AcmWorkbenchPage` / `AcmDiffPage` | 分别展示共享提示、文件操作和运行状态；不直接访问 Node/Electron。                    |
| `AcmPluginNotice`                  | 读取/写入版本化 dismiss marker；进入 ACM 设置时清除 marker。                        |

建议接口：

- `acm:startDiff`：请求 `{reference, candidate, stdin}`，返回 `{taskId}`。
- `acm:stopDiff`：停止当前对拍，返回是否存在活动任务。
- `acm:diffEvent`：事件 `{taskId, side, stage, status, result?, cleanupWarning?, terminationError?, cleanupBlocked?, cleanupConfirmed?}`；终结事件中的 `result` 携带两侧受限制的 stdout/stderr 和首个差异。终止未确认时先报告 `cleanupBlocked`，迟到 `exit/close` 确认并完成清理后再发送 `cleanupConfirmed`，Renderer 在此之前保持 busy。
- `acm:diffDismissNotice` / `acm:diffNoticeState`：持久化提示 marker，值包含 `productVersion`、`dismissed` 和 `reason`。

结果状态集合：

`reference-failed`、`candidate-compile-failed`、`candidate-runtime-failed`、`candidate-timeout`、`candidate-output-limit`、`match`、`mismatch`、`cancelled`、`unsupported`。

## 技术方案比较

| 方案                                                                                     | 优点                                                                             | 缺点                                                                             | 结论                                     |
| ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | ---------------------------------------- |
| 方案 A：新增 `AcmDifferService`，内部复用 Runner helper/Compiler，双任务事件由新契约表达 | 不改变单文件 Runner 的状态机；标准程序门禁和双方结果可明确建模；可独立测试和停止 | 增加一层编排与少量重复的临时目录/流收集逻辑                                      | **采用**，与当前单文件 Runner 边界最相容 |
| 方案 B：把 `AcmRunnerService` 扩展成任意 N 个 side 的通用流水线                          | 复用更多执行代码，未来多文件/批量测试可扩展                                      | 破坏现有 Runner 事件语义和 UI；并发/串行、标准程序门禁、清理结果会使旧契约复杂化 | 暂不采用，待真实批量需求确认后再评估     |

比较器方案：

- token 数组一次性驻留内存：实现简单、首差异定位稳定；输出上限 4 MiB 使最坏内存可控，采用该方案。
- 流式 token 比较：更省内存，但需要跨 chunk 保存 token 边界和上下文，且不必要地增加错误面，暂不采用。

## 数据与迁移影响

- 不新增 SQLite 表，不改变备份格式；对拍源码、stdin、结果和 dismiss marker 不写入数据库备份。
- 提示 marker 属于便携设置，需将当前 ACM 设置从 `{enabled}` 扩展为 `{enabled, noticeDismissedVersion?}`，并保持 v1→v2 默认值兼容；版本变化由主进程当前 `RELEASE_CONFIG.productVersion` 比较。
- 用户主动打开 ACM 设置时清除 marker；插件禁用时页面读取状态并强制显示提示，不改变插件实际 enabled 值。

## 风险与缓解

1. 待测源码不设固定产品输入长度上限，可能增加 Renderer/IPC/临时文件的瞬时压力；保留标准程序 2 MiB 边界，并通过 staging 前后 UTF-8 字节预检、编译/运行超时、stdin、stdout/stderr 和 128 MiB 临时目录限制控制执行期资源，超限时返回稳定错误码。当前 IPC 仍以单次字符串传输，超大粘贴可能短暂增加 V8/主进程峰值；文件打开和外部检查使用异步分块读取、增量哈希，保存使用异步临时替换和有界队列，但编辑器仍需保留完整文本，流式 IPC/backpressure 和更细粒度的活动页面预算留作后续资源隔离迭代。
2. 标准程序和待测程序输出可能达到上限；主进程按现有 4 MiB 限制截断并终止对应任务，IPC 只发送受限输出，Renderer 使用可滚动纯文本区域避免布局膨胀。
3. 一个程序结束后可执行文件被 Windows 锁定；每侧独立清理、有限重试，清理警告与比较结果分离，并在下次 Runner 初始化继续清理。
4. 双侧任务停止或超时发生竞态；每个 side 使用独立 task id/phase，活动任务只允许一个，停止、超时、输出超限和流错误都会执行有限终止尝试；终止未确认时保留 child/active 跟踪和临时目录，并在晚到 `exit/close` 后继续清理，避免服务在失去进程跟踪后放行下一次任务。插件禁用、重试和 Runner/对拍任务准入共享主进程 ACM 生命周期串行队列；可取消的开始请求在准入后 detached 执行，使停止/禁用不必等待编译器探测完成。
5. 持久化关闭提示可能掩盖插件状态；marker 仅控制提示可见性，disabled/unsupported/error 状态始终强制显示，并在设置入口清除 marker。
6. 两份代码使用不同临时目录但共享同一编译器；编译路径和环境通过现有 helper 的受控 PATH 构造，并将子进程 `TEMP/TMP` 指向对应 side 目录，使编译器中间文件纳入目录配额，避免用户 PATH 或远程输入进入命令行。该目录配额仍不覆盖程序主动写入的外部路径。

## 测试策略

- 比较器单测：空输出、连续空白/CRLF、首 token 差异、尾部缺失、多余 token、前后文边界和输出上限。
- 服务单测：标准编译失败/运行失败、待测编译失败/运行异常/超时/输出限制、正常 AC/WA、停止竞态、终止失败后 `cleanupBlocked`/活动任务保持、清理失败重试和插件门禁。
- IPC 契约测试：请求大小、空源码、非法状态和 disabled/unsupported 拒绝；终结事件只包含受限 stdout/stderr，并允许报告终止未确认的 `terminationError/cleanupBlocked`，不携带未声明的敏感进程信息。
- IPC/服务边界测试：标准程序超过 2 MiB 时拒绝，待测程序超过原 2 MiB 阈值时仍可进入流水线；运行期资源限制继续覆盖超时、输出和临时目录超限。
- Renderer 测试：双编辑器空初始值、打开/保存/另存为、stdin 丢弃、差异片段展示、提示关闭共享、版本变化/插件禁用重新显示、监听器 cleanup。
- Packaged E2E：独立 `/acm-diff` 路由真实编译/运行 AC 与 WA、标准程序失败、待测程序失败、停止/超时、差异片段、控件恢复、AppX 入口和 ACM disabled gate。
- 安全审计：`PARTIAL`。本轮没有阻断级高危漏洞。已验证 scope 路由边界、临时目录 owner marker 失败回收和子进程临时目录；文件打开/外部变更检查使用异步分块读取和增量哈希，打开检查/保存队列/另存为对话框 admission 和退出等待覆盖文件操作生命周期；对拍和 Runner 对手动停止、自动超时、输出超限及流错误统一执行有限终止尝试，终止未确认时带 `terminationError/cleanupBlocked` 并保留活动任务和临时目录，晚到 `exit/close` 后再清理；运行中和启动时的清理重试/旧目录回收都会重新检查根目录及目录内部 reparse point，并由处置等待已登记重试。Windows 句柄级 no-follow/原子替换、候选源码 IPC 峰值、底层调用永久挂起、应用退出后未确认子进程可能残留，以及 Runner 非沙箱仍是 P2/P3 残余风险。替换成功后的 `.bak` 清理失败现在不回滚保存结果，而是通过 `IpcResult.warnings` 返回提示并最多后台重试 3 次，Renderer 两页均展示 warning。原生对话框若永久不返回仍会拖延退出；页面卸载或服务释放后的打开/另存为请求会丢弃迟到结果，并取消大文件读取或覆盖写入登记。崩溃后遗留的 pid-uuid `.bak` 已由文件服务启动扫描回收。操作系统级不可信代码沙箱和完整字符串 IPC 不在本版本实现范围，相关残余风险按主计划记录。

## 未解决但不阻断第一版的问题

- 不做批量输入文件、对拍历史、随机生成器、多文件工程、并行运行或调试器。
- 完整 Release 性能、Store 安装和多 Windows 宿主矩阵仍按主计划单独验收；如需支持不可信源码，还必须先补充 Windows 受限令牌/AppContainer/网络隔离等沙箱设计和验收。
- 文件服务的原生对话框若永久不返回仍会拖延退出，Windows 句柄级 no-follow/原子替换留作后续安全迭代；页面卸载或服务释放后的打开/另存为请求已按 generation 丢弃迟到结果。当前 `.bak` 清理已采用保存成功 + warning + 最多 3 次后台重试，并在启动时扫描回收崩溃遗留的 pid-uuid 备份。
